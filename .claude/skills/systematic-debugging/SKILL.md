# Systematic Debugging（体系的デバッグ）

## 原則

当てずっぽうの修正は時間を溶かし、新しいバグを生む。応急パッチは根本問題を隠す。

**鉄則: 根本原因の調査なしに修正を試みない。症状への対処で終わるのは失敗。**

```
NO FIXES WITHOUT ROOT CAUSE INVESTIGATION FIRST
```

Phase 1 を終えていないなら、修正を提案する資格がない。

## 適用対象

テスト失敗 / 本番バグ / 予期しない挙動 / 性能問題 / ビルド失敗 / 結合問題 / verifier の fail verdict — すべて。

**特に以下のときこそ使う（スキップしたくなるときほど必要）:**
- 時間的プレッシャーがある（焦りは当て推量を誘発する）
- 「すぐ直せそうな1行修正」が見えている
- すでに複数回修正を試みた / 前の修正が効かなかった
- 問題を完全には理解できていない

## 4つのフェーズ（順番厳守）

### Phase 1: 根本原因調査 — 修正前に必ず

1. **エラーメッセージを最後まで読む** — stack trace 全体、行番号、エラーコード。答えが書いてあることが多い。
2. **一貫して再現させる** — 再現手順は？毎回起きるか？再現できないなら推測せずデータを集める。
3. **直近の変更を確認** — git diff / 直近 commit / 依存・config・環境の差分。
4. **多層システムでは各層を計装してから仮説を立てる** — CI→build→署名、API→service→DB のような構成では、各コンポーネント境界で入る値と出る値をログし、**どの層で壊れるかの証拠を先に取る**。証拠が示した層だけを調査する。
5. **データフローを遡る** — エラーが call stack の深部にあるなら、不正な値の発生源まで遡って発生源で直す（詳細: `root-cause-tracing.md`）。

### Phase 2: パターン分析

1. 同じ codebase 内の**動いている類似コード**を探す
2. リファレンス実装があるなら**完読**する（流し読み禁止）
3. 動くものと壊れているものの**差分をすべて列挙**（「これは関係ないだろう」を禁止）
4. 依存・設定・前提条件を洗い出す

### Phase 3: 仮説と検証

1. **仮説は1つずつ**明文化する:「Y だから X が根本原因だと考える」
2. 仮説を検証する**最小の変更**を1つだけ入れる（複数同時修正の禁止）
3. 効いた → Phase 4 へ。効かない → 修正を積み増さず、**新しい仮説**へ戻る
4. 分からないなら「X が分からない」と言う。知ったかぶりで進めない

### Phase 4: 実装

1. **失敗する再現テストを先に作る**（framework が無ければ使い捨てスクリプトでも可）
2. 根本原因に対する**単一の修正**を入れる（「ついで」のリファクタ禁止）
3. テスト通過・他テスト非破壊・元症状の解消を確認
4. **修正が効かなかったら試行回数を数える**:
   - 3回未満 → 新情報を持って Phase 1 へ戻る
   - **3回以上 → 修正をやめてアーキテクチャを疑う**

### 3回失敗ルール: アーキテクチャを疑え

修正のたびに別の場所で新しい症状が出る / どの修正も大規模改修を要求してくる —
これは仮説の失敗ではなく**設計が間違っているサイン**。修正4回目を試みる前に、
このパターン自体が健全かを問い直し、ユーザー（または Dispatcher）に相談する。

> **squad worker として動いている場合**: これは検証ゲートの
> 「verify 3回 fail → `status: blocked` で報告」とちょうど対応する。
> blocked 報告の `notes` には、試した仮説と「なぜアーキテクチャ起因と考えるか」を書く。
> それが次の担当者（人間 or 再発注 worker）の Phase 1 になる。

## Red Flags — こう考え始めたら STOP して Phase 1 へ

- 「とりあえずこれを変えて様子を見よう」
- 「複数箇所まとめて直してテストを流そう」
- 「たぶん X だから直しておこう」
- 「完全には理解してないけど、これで動くはず」
- 「もう1回だけ修正を試そう」（すでに2回以上失敗している）
- 調査の前に修正候補のリストを提示している

## よくある言い訳と現実

| 言い訳 | 現実 |
|--------|------|
| 「単純な問題だからプロセス不要」 | 単純なバグにも根本原因はある。単純ならプロセスも速く終わる |
| 「緊急だから時間がない」 | 体系的デバッグは guess-and-check の試行錯誤より**速い** |
| 「まず試して、ダメなら調査する」 | 最初の1手が習慣を決める。最初から正しくやる |
| 「修正を確認してからテストを書く」 | テスト無しの修正は定着しない。先に失敗を固定する |
| 「リファレンスは長いので要点だけ真似る」 | 部分理解はバグを保証する。完読する |

## 「根本原因なし」で終わってよい条件

調査の結果、真に環境依存・タイミング依存・外部起因だと判明した場合のみ:
調査内容を記録し、適切なハンドリング（retry / timeout / エラーメッセージ）と
監視・ログを入れて完了とする。ただし「根本原因が見つからない」の95%は調査不足。
