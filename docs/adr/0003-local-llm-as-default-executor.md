# ADR 0003: 仕様が確定したコード変更はローカル LLM (local-coder) に既定で委譲する

- **Status**: Accepted
- **Date**: 2026-08-19
- **Supersedes**: なし
- **Related**: [ADR 0001](0001-multi-session-isolation-by-project-ownership.md),
  [ADR 0002](0002-squad-cli-wrapper.md)

## Context

`instructions/dispatcher.md` にはローカル LLM (当時 `qwen-consultant`、のち
`vllm-consultant`) の節があり、用途は task YAML の lint とログの一次要約に
限定されていた。コードレビュー・複数ファイル横断・仕様やテストの生成は禁止で、
その根拠は「Qwen の誤検知率が高い」という運用上の実感だった。

前提が 2 つ変わった。

1. **配信モデルが変わった**。LAN の vLLM は Nemotron 3.5 Lightning
   (30B-A3B NVFP4、`nemotron-35-lightning`、文脈 65,536) を配信している。
   禁止の根拠だった Qwen は動いていない。
2. **実測が揃った**。`~/work/llm-stack/docs/phase3-report.md` および
   `phase5-report.md` で、ハーネス 4 種 × モデル 2 種 × 並列度 4 水準を測った。
   測ったタスクは自前の spec-fidelity タスク 3 種、すなわち**仕様を渡して
   閉じた文脈でコードを直させる**もので、396 試行でほぼ全問正答、1 件 20-60 秒。

一方で、その実測は squad が local-coder に期待しうる他の用途を**まったく
カバーしていない**。正答率が 4 フェーズ通して判別しなかったのは、タスクが
仕様追従の編集だったからであり、レビュー品質・仕様生成能力・長文脈での品質に
ついては情報がゼロである。

選択肢:

- **A. 現状維持 (lint と要約だけ)** — 実測で裏が取れた領域を使わないまま、
  トークンコストゼロの実行能力を遊ばせることになる
- **B. 全面的に解禁する** — 禁止の根拠 (旧 Qwen) が消えたことを「良いと分かった」と
  取り違える。レビューも仕様生成も未測定のまま本番に入る
- **C. 実測した範囲に限って既定の実行担当に引き上げ、それ以外は根拠を
  「測っていない」に差し替えて残す**

## Decision

**C を採用**。`instructions/dispatcher.md` と `instructions/worker.md` に
「ローカル LLM (local-coder) への委譲」の節を置き、以下を定める。

### 委譲の条件 (すべて満たすこと)

1. task YAML に `verify:` があり、コマンドが機械検証できる
2. 仕様が task YAML に書き出されている (自分で仕様を決める必要がない)
3. 単一〜数ファイルで、横断的な再設計を伴わない
4. 渡す文脈が 50k トークン以内 (上限 65,536 に生成ぶんの余裕を残す)

条件を満たすタスクは worker の判断で既定として委譲する。判断は Dispatcher では
なく worker が行う。失敗しても `verify:` で落ちるだけでトークンコストはゼロなので、
迷ったら委譲してよい。

### 委譲しないもの

コードレビュー・並行性の検討、複数ファイル横断・大規模リファクタ、仕様やテストの
生成、外部情報が要るもの。**根拠は「品質が悪い」ではなく「測っていない」である。**
測れば広げてよく、広げるときは実測を先に行う。

### ガードレール (いずれも実測由来)

- **合否は `verify:` のコマンドと差分の目視で決める。** local-coder の自己申告は
  判定に使わない。仕様の取り違えは出力から見えない (直感に逆らう仕様を過剰適用して
  落ちた実例がある)
- **健全性は終了ステータスで見る。** 結果が正常に見えても異常終了していることがある
  (出力上限超過で毎回 400 を返しながらスコアは満点のまま、という実例)
- **壁時計 300 秒で打ち切る。** 並列 4 での実測 p95 が 60 秒であり、その 5 倍
- **打ち切ったら作業結果を捨ててやり直す。途中から再開しない。** 暴走した試行は
  「何もしなかった場合より悪い」状態を残す (reward 0.0 < nop ベースライン 0.25)
- **委譲 1 件につき LLM ストリームが 1 本増える。** vLLM は同時 8 本まで受け、
  超えた分はエラーにならず無言で待ち行列に入る。squad 全体で同時 4 件までに抑える
- **pane のモデル切り替え (`notify-worker.sh --model`) とは別の層である。**
  worker 自体をローカルモデルに切り替えてはならない (web search と
  サブエージェントを失う)

## Consequences

- **良い点**:
  - 仕様が確定した実装のトークンコストがゼロになる。squad で最も件数の多い
    タスク種別であり、Claude の token を設計・レビュー・横断実装に回せる
  - 委譲の可否が `verify:` の有無という**既存の機械的な条件**に接続される。
    新しい判断軸を増やしていない
  - 禁止の根拠が「未測定」として明示されるので、後から実測で広げられる。
    「悪いと分かっている」という誤読で固定化しない
- **悪い点**:
  - **`local-coder` の agent 定義がまだ存在しない**。`.claude/agents/` にあるのは
    `task-yaml-author` / `dashboard-updater` / `verifier` の 3 つで、
    旧 `vllm-consultant` も定義が無く実体の無い参照だった。この ADR と指示書は
    契約の記述であり、定義が入るまで委譲は発生しない
  - worker の手順が 1 段増える。委譲するかの判断と、返ってきた差分の目視が要る。
    自分で書いたほうが速い規模のタスクでは割に合わない
  - **squad が LAN の vLLM に依存する**。停止時は worker が自分で実装する形に
    戻るため機能は落ちないが、所要時間と token 消費は変わる
  - 実測は文脈 65,536・並列 1-4・spec-fidelity タスク 3 種という条件のもので
    あり、squad の実タスクの分布とは一致しない。**条件が動けば結論も動く**
