# ADR 0004: local-coder のバックエンドを Qwen3.8-Flash-Next に移し、委譲条件を実測で引き直す

- **Status**: Superseded by [ADR 0005](0005-worker-runs-the-local-model-directly.md)
- **Date**: 2026-08-30
- **Supersedes**: [ADR 0003](0003-local-llm-as-default-executor.md)
- **Related**: [ADR 0001](0001-multi-session-isolation-by-project-ownership.md),
  [ADR 0002](0002-squad-cli-wrapper.md)

## Context

ADR 0003 は Nemotron 3.5 Lightning (文脈 65,536) を前提に、委譲条件と
ガードレールを phase3 / phase5 の実測から導いた。その前提が全部動いた。

LAN の vLLM が配信するモデルは Nemotron → Ornith 1.5 → **Qwen3.8-Flash-Next
NVFP4** (文脈 262,144) と 2 回替わっている。ADR 0003 の数値はどれも
Nemotron のものなので、そのまま残すと**根拠を失った数字が条件として効き続ける**。

2026-08-29/30 に `~/work/llm-stack` で 3 本測った。

1. **自前 13 タスク × 3 試行 (39 試行)**: Flash-Next 39/39 PASS。壁時計
   p50 30.2 秒、最悪 322.5 秒。同条件 1 試行の Ornith は 12/13。
2. **並列 1/2/4/8** (phase5 と同条件、pi ハーネス、harbor spec タスク 3 種):

   | 並列 | 満点 | p50 | p95 | 最大 | 正答/分 | GPU 平均 | 実行平均 | 待機最大 |
   |---:|---|---:|---:|---:|---:|---:|---:|---:|
   | 1 | 12/12 | 35 | 61 | 74 | 0.86 | 45% | 0.5 | 0 |
   | 2 | 18/18 | 40 | 92 | 107 | 1.55 | 73% | 1.0 | 0 |
   | 4 | 36/36 | 36 | 97 | 132 | 2.98 | 86% | 2.0 | 0 |
   | 8 | 65/66 | 48 | 118 | 145 | 4.66 | 85% | 4.2 | 0 |

   並列 8 の 4.66 は phase5 の Nemotron (4.12 / 3.29) と Qwen3.8 (4.05 / 3.98)
   のいずれも上回る。例外 0 件で、Nemotron が並列 8 で 902 秒に張り付いた
   不安定さは出ていない。
3. 公表ベンチでは SWE-bench Pro 62.5 / LiveCodeBench v6 91.9 などを主張して
   いるが、評価ハーネスが Claude Code で条件が違う。**採用判断には使わない**。

ADR 0003 が「測っていない」を根拠に禁止した範囲のうち、1 の 13 タスクは
colcon 依存・git・tf・cmake・QoS・スキャン処理を含み、spec-fidelity 3 種より
広い。ここは実測で埋まった。レビュー品質・仕様生成・長文脈での品質は
**依然として未測定**である。

## Decision

ADR 0003 の構造 (条件を満たすものだけ既定で委譲する) は維持し、
**数値の根拠を Flash-Next の実測に差し替える**。

### 委譲の条件 (変更は 4 のみ)

1. task YAML に `verify:` があり、コマンドが機械検証できる
2. 仕様が task YAML に書き出されている
3. 単一〜数ファイルで、横断的な再設計を伴わない
4. **渡す文脈が 200k トークン以内** (上限 262,144 に生成ぶんの余裕を残す)

### ガードレール (0003 から変える 3 点)

- **壁時計 900 秒で打ち切る** (0003 は 300 秒)。**0003 の 300 秒は
  そのままだと正当な実行を殺す。** 根拠だった「並列 4 の p95 60 秒 × 5」は
  Nemotron の値で、Flash-Next は並列 4 の p95 が 97 秒、直列の最悪ケースが
  322 秒ある。同じ 5 倍則を Flash-Next の p95 に当てると 485 秒だが、
  直列最悪の 322 秒に対しても余裕を持たせて 900 秒とする
- **同時 8 件まで許す** (0003 は 4 件)。並列ベンチで待機キューは全水準 0 で、
  vLLM の `--max-num-seqs 8` に一度も当たらなかった。エージェントは編集や
  テストの間 LLM を叩かないので、名目並列 8 でも vLLM 上で走るのは平均
  4.2 本にとどまる。ただし GPU 使用率は並列 4 で 86% に達し 8 でも 85% で
  頭打ちなので、**8 に増やしてもスループットは線形には伸びない**
  (0.86 → 1.55 → 2.98 → 4.66)
- **合否と健全性の見方は変えない**。`verify:` のコマンドと差分の目視で決め、
  自己申告は使わない。異常終了はステータスで見る。打ち切ったら結果を捨てて
  やり直す。いずれも 0003 のまま有効

### 委譲しないもの (0003 から変えない)

コードレビュー・並行性の検討、複数ファイル横断・大規模リファクタ、仕様や
テストの生成、外部情報が要るもの。**根拠は引き続き「測っていない」である。**

### 接続構成の変更

pi / opencode の接続先を vLLM 直 (8000) から **litellm (4000) 経由**に変える。
GPU は 1 枚で LLM サービスは同時 1 つしか動かせず、モデルを替えるたびに
ポートが動くため。litellm を挟むと baseUrl を固定したままモデル名だけで
切り替えられる。Flash-Next の `reasoning_effort` 既定は xhigh で、指定しないと
実測で壁時計 4 倍になるが、litellm 側で medium を注入するのでこの経路なら
取りこぼさない。

## Consequences

- **良い点**:
  - 文脈上限が 4 倍になり、条件 4 で弾かれていたタスクを委譲できる
  - 打ち切りが実測に接続され直した。300 秒のままなら Flash-Next の正当な
    実行を打ち切り、「暴走した」と誤認する事故が起きていた
  - 委譲可能と裏付けられたタスク種別が spec-fidelity 3 種から 13 種に広がった
  - litellm 経由にしたことで、モデル切り替え時にクライアント設定を
    書き換える箇所が `model` の 1 行だけになる
- **悪い点**:
  - **Flash-Next はマシンを占有する**。VRAM 92.5 GiB、ホスト RAM 100 GiB を
    使い (PLE 95.4 GiB が常駐)、他の重い処理と同居できない。Ornith は
    VRAM 22.4 GiB だったので、この点は明確な後退
  - **起動が 405 秒** (Ornith は 125 秒)。落ちたときの復帰が遅い
  - **最悪ケースが悪化した**。直列の実測で p50 30 秒に対し最悪 322 秒と
    10 倍の開きがある。打ち切りを 900 秒に伸ばしたぶん、暴走した試行を
    抱える時間も伸びる
  - **重みが `/mnt/data` (nvme1n1) に依存する**。173.6 GiB あり
    ルートディスクには入らない。このディスクが死ぬと復旧に 2 時間半かかる
  - 比較の非対称が残る。Ornith は 1 試行しか測っておらず、13 タスクでの
    12/13 対 39/39 は厳密な対戦成績ではない
  - **接続先ホストの持ち方**。ADR 0003 は「`baseUrl` の IP がリポジトリに
    直書きされる」を負債として挙げていた。本 ADR ではこれを解消し、
    `config/pi/models.json.template` を `scripts/link-pi-config.sh` が
    `LLM_HOST` で展開する方式にした。代償として symlink ではなく生成ファイルに
    なったので、**テンプレートを編集したら再実行が要る**。張り忘れると
    agent はあるのに接続先が古い、という 0003 が警戒した壊れ方に戻る
  - **公表ベンチとの突き合わせをしていない**。SWE-bench 系の主張が本 squad の
    worker 用途に対応するかは未検証で、判断には使っていない
  - Sonnet との同条件比較が未実施。ADR 0003 から続く「Sonnet worker を
    ローカルで置き換えられるか」という問いには、まだ数字で答えられていない
